# ADR-002: Run NordVPN over a native IKEv2 profile, not the NordVPN app

- **Status:** Accepted; amended 2026-08-17: LAN fallback for Tailscale-off, see ADR-003
- **Date:** 2026-08-16
- **Supersedes:** [ADR-001](adr-001-hostname-resolution.md) (hostname resolution strategy; its `/etc/resolver`
  decision was never applied)

## 1. Context

ADR-001 diagnosed a DNS collision that broke bare-hostname resolution (and,
per `dns-config-lsy` and `dns-config-4ev`, general internet connectivity)
whenever NordVPN and Tailscale were both active. That diagnosis was correct
about the mechanism but incomplete about the cause: it was written on the
assumption that the collision was inherent to running "NordVPN" and
Tailscale together. It is not. The collision is an artifact of the
**NordVPN app's** tunnel implementation specifically.

### The collision, precisely

The NordVPN macOS **app** connects via its NordLynx (WireGuard-based) tunnel
extension, which installs a DNS resolver at `100.64.0.2` (`utun11`, measured
in ADR-001's Context). `100.64.0.0/10` is the RFC 6598 Carrier-Grade NAT
range, and Tailscale claims and routes the entire range for its own tailnet
addressing (`100.64.10.4` for streamy, etc., on `utun17`/`utun20`
depending on the session). With both tunnels up, Tailscale's route claim on
`100.64.0.0/10` captures traffic addressed to Nord's own nameserver, so
queries to `100.64.0.2` are routed into the tailnet and black-holed there
instead of reaching Nord's resolver.

Because macOS elects a single **primary** DNS-serving network service based
on which service holds the default route (`dns-config-c15.3` comment,
2026-08-16 00:04 — Apple's `ip_plugin.c`: "don't elect a service to be
primary if it doesn't have a default route"), and the NordVPN app's tunnel
holds the default route while Tailscale does not, Nord's resolver becomes
primary. Every DNS query on the machine — not just tailnet lookups — is then
sent to the black-holed `100.64.0.2` first. This is why the observed failure
mode was total: "the Mac appears to have no network" (`dns-config-4ev`
description), not merely "tailnet names fail to resolve."

The same address collision also produces a **routing** failure, tracked
separately in `dns-config-lsy`: with the NordVPN app's tunnel up, Tailscale
peer traffic and Tailscale's own control-plane connection to
`controlplane.tailscale.com` degrade or die outright, independent of DNS.
`snapshots/ts-then-nord-2.log` (committed) captures this directly: with the
app's tunnel started on top of a healthy Tailscale session, tailnet ping and
tailnet DNS both fail within seconds of Nord coming up, while the WEB column
(a real HTTPS fetch, the decisive signal per that log's own header) also
goes bad. `snapshots/openvpn-udp-nord.log` (committed) shows the same
collapse pattern when the app is configured to use OpenVPN-UDP instead of
NordLynx, ruling out "switch the app's own protocol setting" as a fix — the
app's tunnel captures `100.64.0.0/10` addressing regardless of which
underlying VPN protocol it uses.

A third, independent failure mode is a **startup-ordering deadlock**: if the
NordVPN app's tunnel is brought up *before* Tailscale, Tailscale can be left
in a `NeedsLogin`/Logged-Out state rather than reconnecting, per
`dns-config-qsk.10`'s Phase 3 step 6 guidance (deliberately not run further
by script — "do not log in via script; tell the human"). Bringing Tailscale
up first and the app's tunnel up second avoids the deadlock but does not
avoid the DNS/routing collision (see `dns-config-4ev` comment, 2026-08-16
08:31, the human's report that the browser does not work while NordVPN is
up even with the good ordering).

Every locally-exhausted attempt to fix this from the NordVPN app's side, or
from Tailscale's side, is recorded on `dns-config-4ev` and
`dns-config-vb2` (see Alternatives, below); none of them worked, because all
of them left the app's tunnel — the actual source of the `100.64.0.2`
resolver — in place.

## 2. Decision

**Run NordVPN via a native IKEv2 configuration profile, generated by
[`bin/nord-ikev2-profile.sh`](../bin/nord-ikev2-profile.sh) and installed
per the runbook at
[`docs/switcher/nord-ikev2-setup.md`](switcher/nord-ikev2-setup.md), instead
of the NordVPN app's own tunnel.**

- Do **not** run the NordVPN app's tunnel (NordLynx or its OpenVPN option)
  alongside Tailscale. The app is the source of the collision; if the app's
  tunnel is connected, the collision returns regardless of anything else in
  this document (see Consequences, below).
- Do **not** install `/etc/resolver` (ADR-001's original decision). It is
  unnecessary: NordVPN's IKEv2 servers push a resolver outside
  `100.64.0.0/10`, so there is nothing for Tailscale's route claim to
  capture, and bare tailnet names resolve correctly with the system's normal
  resolver selection — no domain-scoped override needed.

## 3. Evidence

All figures below are quoted from `dns-config-qsk.10`'s comments
(2026-08-16), measured on this machine with the NordVPN app disconnected so
results are attributable to the IKEv2 profile alone.

**First connect** (IKEv2 up, Tailscale off, Nord app disconnected):

> tunnel: ipsec0, inet 10.6.0.41 (NOT a utun; NOT inside 100.64.0.0/10)
> resolver#1: nameserver[0] 103.86.96.100, nameserver[1] 103.86.99.100, if_index 46 (ipsec0)
> 100.64.x resolvers anywhere in scutil --dns: NONE
> default route: link#46 via ipsec0 (plus en0 fallback)
> web: 200 in 0.172s   egress: 187.40.54.188 (Nord)

**Both up** (Tailscale brought up on top of a live IKEv2 tunnel — the
ordering that deadlocked under the app):

> ts_up -> ts_wait_for Running: rc=0 in 1 SECOND. No NeedsLogin, no registration deadlock.
> Both up: ipsec0 10.6.0.41 (Nord) AND 100.64/10 claimed on utun20 (Tailscale).
> Resolver stack: #1 100.100.100.100 (utun20), #2 103.86.96.100 (ipsec0), #3 100.100.100.100.
> Nothing captured — Nord's resolver is outside CGNAT space.
> web=200, egress=187.40.54.188 (Nord's IP — traffic still exits via Nord),
> streamy dns=100.64.10.4, streamy ping ok, streamy:5000 open, mac-mini:22 open.

**60-second soak**, 12 samples at 5s intervals:

> ipsec0=up, web=200, streamy-dns ok, streamy-ping ok — 12/12. Zero degradation.

**PMTU**, tailnet address `100.64.10.4`, both up:

> 1252 PASS / 1300 FAIL — identical to Tailscale-alone baseline (1280 MTU - 28).
> Nord IKEv2 adds no MTU penalty on the tailnet path.

**DNS verification**, both up:

> bin/dns-verify.sh with BOTH UP: 6/6 PASS.

**Durability — Tailscale restart under a live IKEv2 tunnel:**

> ts_down -> Stopped. ipsec0 still 10.6.0.41 (Nord unaffected). web=200,
> egress=187.40.54.188 (Nord), resolver#1=103.86.96.100.
> ts_up -> Running in 1s. ipsec0 still 10.6.0.41. web=200,
> streamy=100.64.10.4, streamy:5000 open.

## 4. Consequences and tradeoffs

- **Throughput: UNMEASURED.** IKEv2 vs. NordLynx throughput has not been
  measured on this machine. `dns-config-qsk.11` is filed to measure it; do
  not assume parity or a penalty either way until that measurement exists.
- **No Threat Protection.** The app's malware/ad/tracker-blocking feature is
  app-only and is not available over a bare IKEv2 profile.
- **No kill switch.** The IKEv2 profile has no equivalent of the app's kill
  switch; a dropped tunnel fails open to the underlying network path rather
  than blocking traffic.
- **One pinned server**, `de1545.nordvpn.com`, baked into the generated
  profile. Server rotation requires regenerating the profile with
  `bin/nord-ikev2-profile.sh`, not a live server switch inside an app.
- **Plaintext credential.** The profile stores the NordVPN service password
  in plaintext inside the generated `.mobileconfig`. It is kept at mode 600
  and outside this repository, but it is not encrypted at rest.
- **Not addressable by `scutil --nc`.** Verified: the profile-installed
  IKEv2 configuration cannot be started or stopped via `scutil --nc`, by
  display name, by the profile's `PayloadUUID`, or by any of the five
  configuration UUIDs found in
  `/Library/Preferences/com.apple.networkextension.plist` — every attempt
  returns "No service." Root cause: `scutil --nc` enumerates
  SystemConfiguration network services; NetworkExtension personal-VPN
  configurations (which is what a user-installed IKEv2 profile creates) live
  in a separate NetworkExtension store that `scutil --nc` does not see, and
  this is true regardless of install scope.
- **Programmatic on/off is via Shortcuts, not scutil.** The only viable
  control handle found is the Shortcuts "Set VPN" action, invoked
  non-interactively with `shortcuts run "NordVPN On"` / `shortcuts run
  "NordVPN Off"`. This requires **two Shortcuts that a human must create**
  in Shortcuts.app (Apple's Shortcuts CLI can run and list shortcuts but
  cannot create or import one non-interactively): a shortcut named exactly
  `NordVPN On` using the "Set VPN" action targeting `NordVPN IKEv2` in
  Connect mode, and one named exactly `NordVPN Off` in Disconnect mode.
  **`shortcuts run` returns exit code 0 even when the named shortcut does
  not exist** (it prints "Couldn't find shortcut" but the process exit
  status is still 0), so any caller of `shortcuts run` for Nord control must
  independently verify reality (tunnel `inet` address present/absent plus
  the `103.86.x` resolver) after invoking it, exactly as the existing
  Tailscale control library verifies `tailscale status` rather than trusting
  a command's exit code alone. Device-scope profile installation via
  `profiles install` is not a fallback: that subcommand has been removed on
  this macOS ("profiles tool no longer supports installs. Use System
  Settings"), and per the above it would not have made the configuration
  `scutil --nc`-addressable in any case.
- **The NordVPN app must not be connected concurrently.** Running the app's
  tunnel alongside the IKEv2 profile is an unsupported, untested
  configuration and is expected to re-create the exact collision this ADR
  exists to avoid — the app's tunnel is what installs the `100.64.0.2`
  resolver, not something specific to NordLynx as a protocol
  (`snapshots/openvpn-udp-nord.log` shows the same failure with the app set
  to OpenVPN). Note additionally that the app's kill switch was **observed enabled**
  on this machine (`nord-surfaces.md`: `killSwitchEnabled = 1`), so simply launching the app to check something can itself
  interrupt connectivity independent of the DNS collision.
- **With Tailscale off, tailnet names are still unavailable by construction**
  — that has not changed. But bare names no longer go unanswered: ADR-003
  (see [`adr-003-lan-fallback.md`](adr-003-lan-fallback.md)) adds a LAN
  fallback that resolves bare `streamy` / `mac-mini` to LAN IPs at home
  via a local dnsmasq resolver for `home.arpa`. As part of that design, the
  IKEv2 profile generated by `bin/nord-ikev2-profile.sh` now also carries a
  DNS dictionary (`DNS.SearchDomains=[home.arpa]`) so bare names keep
  expanding correctly while the Nord IKEv2 tunnel is the primary network
  service.

## 5. Alternatives considered

### `/etc/resolver` domain-scoped entry — unneeded

ADR-001's original decision. Mechanically sound — a domain-scoped
`/etc/resolver` entry wins for `*.tailXXXX.ts.net` by longest-suffix
specificity, which macOS evaluates before resolver `order` (source-code
evidence recorded on bead `dns-config-c15.3`, comment of 2026-08-16 00:04;
note that ADR-001 §1's own `104800 > 101600` sentence is the superseded,
incorrect explanation — see ADR-001's banner) — but it only ever
would have fixed resolution of `*.tailXXXX.ts.net` names — it does nothing
for the general-internet DNS blackout, which was the more severe symptom
(`dns-config-4ev`: "the Mac appears to have no network"). With the
collision removed at its source (this ADR), no resolver-level workaround is
needed for either problem. Never installed.

### Apple DNS-settings configuration profile (`com.apple.dnsSettings.managed` / `NEDNSSettingsManager`) — unneeded

Considered as the Apple-endorsed successor to `/etc/resolver`
(`dns-config-c15.3` comment, 2026-08-16 00:03, citing Apple DTS: "the
classic resolver.conf infrastructure is a compatibility measure, not the
source of truth"). Its plain-UDP-DNS feasibility for a MagicDNS-style target
was never fully established before this ADR made the question moot for the
same reason as `/etc/resolver`: with no collision, no DNS-level workaround
of any kind is required.

### Every NordVPN-app-side and Tailscale-side fix — refuted by measurement

All recorded on `dns-config-4ev` and `dns-config-vb2`; every one left the
app's tunnel in place and so left the collision in place:

- Nord custom DNS (pointed at `1.1.1.1`) — refuted: changes the app
  tunnel's upstream resolver, not the `100.64.0.2` address it publishes to
  the system.
- Nord split-tunnel excluding `100.64.0.0/10` — unavailable: split
  tunnelling is app-based on macOS and the needed exclusion mode is
  Linux-client-only.
- Tailscale `ExitNodeAllowLANAccess` tuning — not applicable to this
  collision (governs LAN access through an exit node, not CGNAT resolver
  capture).
- Demoting Nord via `networksetup -ordernetworkservices` — non-fix: service
  order cannot override macOS's primary-service election while the app's
  tunnel holds the default route.
- Startup ordering (Tailscale up, then the app's tunnel) — partial only:
  avoids the app-first registration deadlock, but "the browser still does
  not work" (paraphrase of the human's report recorded on `dns-config-4ev`,
2026-08-16 08:31 comment) — DNS/routing
  collision persists.
- Tailscale userspace networking mode — unavailable on the macOS GUI
  client (confirmed: the `/usr/local/bin/tailscale` binary is a 68-byte shim
  into the Network Extension app build, which does not expose
  `--tun`/`--userspace`). Available via the Homebrew `tailscaled` binary,
  but rejected on requirements grounds even where available: userspace mode
  is a SOCKS/HTTP proxy with no kernel route, so only apps explicitly
  pointed at it can reach the tailnet — `ssh`, Finder shares, and native
  media-streaming apps cannot without per-app wrapping, and those are
  exactly the use cases in scope.
- Tailscale `--accept-routes=false` — refuted: the capture that breaks
  the collision (Nord's `100.64.0.2` routing into the tailnet) was verified
  still present with the flag off; `tailscale set --help` / `tailscale up
  --help` / `tailscale debug --help` expose no lever that changes
  Tailscale's claimed `100.64.0.0/10` range (consistent with
  `tailscale/tailscale#1381`, open since Feb 2021 — Tailscale requires the
  full range to operate and does not make it configurable).
- Meshnet (NordVPN's own mesh-networking feature) and Nord service ordering
  / `ipPool` settings — investigated and found not to change the
  `100.64.0.2` publication or the routing capture; the app's tunnel is the
  fixed point common to every one of these attempts.

### Mullvad add-on (Tailscale's built-in Mullvad exit-node feature) / off-host exit node — valid but heavier

Not adopted for this ADR, but not refuted either — a legitimate alternative
noted for the record. The Tailscale Mullvad add-on installs no second VPN
client at all, sidestepping this whole class of collision structurally, and
an off-host (e.g., router- or VPS-based) commercial-VPN exit node keeps any
tunnel entirely off this Mac. Both are heavier changes (new provider
relationship or new infrastructure) than "generate one IKEv2 profile," and
were not needed once the IKEv2 path was confirmed to work. See
[`docs/research/community-reports.md`](research/community-reports.md) for
the supporting research, including confirmed Mullvad/Tailscale CGNAT-range
collisions of the same shape on other platforms (§A1, §B2) and their
workarounds, and the site-blocking/streaming/governance caveats recorded
against Mullvad specifically.

## 6. Open questions

1. **NordVPN support's reply.** A support ticket has been drafted/sent
   (`dns-config-4ev`) asking why the app publishes `100.64.0.2` when its own
   IKEv2 servers push `103.86.96.100`/`103.86.99.100`. Their answer could
   change this decision (e.g., if a future app version stops using CGNAT
   space).
2. **Whether the app ever moves off `100.64.0.2`.** If NordVPN changes the
   app's tunnel resolver address in a future release, the collision this ADR
   works around may disappear on its own, at which point running the app
   again could be revisited.
3. **IKEv2 deprecation risk at NordVPN.** IKEv2 is a secondary, non-default
   protocol option for NordVPN; there is no commitment recorded here that
   NordVPN will continue to support it long-term.
4. **Whether to move Nord control into a dedicated app via
   `NEVPNManager`.** Would give real-time `NEVPNStatus` instead of polling
   through Shortcuts, but requires the Personal VPN entitlement (Apple
   Developer Program membership) and was explicitly not pursued without a
   human decision, since it changes cost and packaging
   (`dns-config-qsk.10` comment, 2026-08-16 11:20).
